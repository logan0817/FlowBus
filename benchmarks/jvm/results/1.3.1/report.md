# 1.3.1 sticky 修复的定向性能记录

测量日期：2026-11-11。状态：分配变化已有测量；耗时验收尚未完成。当前记录不能用于宣称提速或无性能回退。

测量使用 Maven Central 正式 1.3.0、未优化的修复候选、优化后的 1.3.1 候选和反向顺序的正式基线。每组均为 JMH 1.37、JDK 17、3 forks、5×1s 预热、5×1s 测量，固定 `-Xms512m -Xmx512m` 和 GC profiler；仅包含 noSubscribers、stickySend、active1 两种模式，共 6 行，不代表完整基准。

## 已确认的分配变化

stickySend 每批发送 128 次，无活跃订阅者。吞吐模式下的分配如下；B/op 指整批分配，不能写成单次事件分配。

| 输入 | B/批次 | 约 B/事件 | 解释 |
| --- | ---: | ---: | --- |
| 正式 1.3.0 首轮 | 15400.1 | 120.3 | 正式基线 |
| 未优化修复候选 | 21544.1 | 168.3 | 比基线增加约 48 B/事件 |
| 单值 replay 优化候选 | 10280.1 | 80.3 | 不再为默认单值 replay 分配树节点/装箱键，并直接读取缓存数量 |
| 正式 1.3.0 反向复测 | 15400.5 | 120.3 | 分配量相近，耗时被后台负载明显扰动 |

JFR 对未优化候选采样发现 TreeMap.Entry、Long、ArrayList/数组等分配，推动了局部修改；采样权重不等于精确每类分配量。优化后仍保留发布序号、代际、取消与锁外恢复契约，反序发送者恢复测试同时覆盖 replay=1 和 replay=2。相关 API、201 core/81 Android/2 示例 JVM 测试和 release lint 通过。

## 耗时为何暂不验收

| 输入 | noSubscribers 批次/ms | stickySend 批次/ms | active1 批次/ms |
| --- | ---: | ---: | ---: |
| 正式 1.3.0 首轮 | 187.25 ± 9.37 | 93.44 ± 4.40 | 25.96 ± 3.92 |
| 未优化修复候选 | 171.87 ± 23.46 | 63.70 ± 11.56 | 25.77 ± 5.17 |
| 单值 replay 优化候选 | 122.90 ± 50.85 | 60.50 ± 15.31 | 23.25 ± 6.19 |
| 正式 1.3.0 反向复测 | 131.77 ± 34.04 | 18.96 ± 9.91 | 0.32 ± 0.26 |
| 正式 1.3.0 后续复测 | 159.04 ± 22.83 | 48.63 ± 24.87 | 9.13 ± 5.23 |
| 优化候选后续复测 | 93.41 ± 31.26 | 43.13 ± 15.94 | 16.72 ± 5.60 |

误差为 JMH scoreError，默认 99.9% 置信区间。未修改的普通发送路径也显著变慢；反向复测时记录到 load≈51、swap 使用约 15 GB，同机其他项目 Gradle 占用 CPU。基线 active1 从约 26 跌至约 0.32 批次/ms，不能将这种差异归因于修复算法。

下一步是在后台负载较平稳时取得正式对照，并结合误差和相同工作量判断耗时。不得挑选有利读数、用 smoke 替代，或停止不属于本任务的进程。本记录不推导 Android ART 性能。

后续复测连续记录 load≈8.9–22.1，同机已知项目 Gradle CPU 峰值约 1.7%，但普通未修改路径仍显示吞吐降低而 SampleTime 缩短的矛盾趋势，无法证明稳定耗时差异。保留这两组作为限制，下一次在 PR 显式启用现有 consumers runner 上的正式对照，不将本机“低于 10%”的个别比值作为通过依据。
